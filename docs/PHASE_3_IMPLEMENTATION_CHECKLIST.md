**3A.1 – 3A.4 rationale (Done 2026-04-21):**
- **Single source of truth** — new module `src/services/scoring/deviation.py` exposes:
  - `DeviationDirection(str, Enum)` — wire values `too_hard` / `too_easy` / `on_target`.
  - `DEVIATION_THRESHOLDS` — frozen V1 threshold table keyed by canonical run_type_key (recovery/easy/tempo/long).
  - `MIN_DEVIATION_DURATION_SECONDS = 600` — the §5-rule-2 floor.
  - `classify_deviation(...)` — pure threshold-classification function (no I/O), unit-testable.
  - `compute_deviation_direction_for_activity(act)` — activity-level adapter that handles all omission cases, planned-type normalization, HR-zone distribution derivation, and target-band-relative pct_above/pct_below computation before delegating to the pure classifier.
- **Derivation policy** — on-read, not persisted. Rationale: (a) avoid invalidation when thresholds evolve (V1.7 Steady/Tempo work); (b) deterministic output from existing persisted inputs (`hr_zone_1..5`, `moving_time`, `planned_type`); (c) §X.5 single-source-of-truth rule — only this module produces the value.
- **Target-band vs acceptable-band (deliberate)** — spec §5 wording "time-above-target" / "time-below-target" does not map to `zone_metrics_for_type`'s acceptable-band semantics (which make `too_easy` unreachable for Long). The deviation module therefore computes pct_above/pct_below relative to `RunTypeDefinition.target_zone_ids` directly. Module docstring "Target-band vs acceptable-band" captures the rationale; Easy/Recovery `too_easy` is unreachable by HR construction (no zone exists below Z1) and that is an intentional characteristic of the V1 HR model.
- **Planned-type vs executed-type zones (CRITICAL)** — `activity.pct_above_zone` / `activity.pct_below_zone` are persisted relative to the *executed* type; deviation must measure against the *planned* type. Adapter re-derives from `hr_zone_1..5` + `planned_type` on every call to avoid the bug. Covered by `test_easy_plan_tempo_execution_is_too_hard`.
- **Tie-breaker** — `classify_deviation` checks `above_exceeded` first so ties resolve to `too_hard` per spec §5 rule 1. Behavior is ordering-sensitive; comment in code calls this out.
- **Wiring** — ``build_run_execution_block`` places `deviation_direction` inside `actual.*` per spec §6 namespace isolation (NOT at block top level). `execution_block_to_insight_summary_shape` surfaces it as a flat key for the LLM `get_run_summary` tool. `/api/plan/current-week` route inherits it automatically via the `**actual` spread into `actual_namespaced` — no per-day-level duplication (the direction is a property of the run, not the plan day).
- **Mobile types** — `smartcoach_app/lib/api/plan.ts` adds `DeviationDirection` union and `deviation_direction?: DeviationDirection | null` on `CurrentWeekActualBlock`, with JSDoc warning mobile MUST NOT re-derive.
- **Testing** — 46 unit cases in `tests/services/scoring/test_deviation.py` locking the threshold table, tie-breaker, every omission branch, target-band-relative derivation, and legacy-key normalization; 5 new cases in `test_run_execution_block.py` for the canonical block + insight-summary adapter; 1 new assertion in `test_plan_current_week_route.py` for end-to-end route surfacing.

**3A.8/9/10 rationale (Done 2026-04-21):**
- **Single source of truth** — new module `src/services/scoring/adherence.py` (colocated with the 0.B `completion.py` primitives under the `scoring/` package so no producer has to reach across service boundaries). Exposes:

  - Named constants `ADHERENCE_LOW_MAX_EXCLUSIVE_PCT = 70.0`, `ADHERENCE_HIGH_MIN_EXCLUSIVE_PCT = 90.0` — no inlined 70/90 literals at call sites.

### 3B.12 — Per-request dedup + profile-update invalidation (2026-04-21)

- **Dedicated in-memory cache.** `src/smartcoach_mobile_coach/user_context_cache.py` mirrors the pattern already used by `insight_cache.py`: threading-safe `dict` keyed by `(user_id, tz, today_iso, schema_version)`, configurable TTL via `SMARTCOACH_MOBILE_USER_CONTEXT_CACHE_TTL` (default 600 s). - **Invalidation on writes.** Three write paths that mutate a `build_user_context_payload` input now call `user_context_cache.invalidate_user_context(user_id)` after their `session.commit()`:
  - `tool_save_coach_preference` — mutates `user_coach_preferences` (drives `coaching.*`).
  - `tool_generate_training_plan` — writes a new plan + plan_workouts row set (drives `race_goal.*`, `plan.*`, `preferences.*`).
  - (Reserved) A future `tool_link_strava_account` will need the same hook for `baseline_status`.
  `invalidate_user_context` drops every cached key under the `user_id:` prefix, so both `UTC` and `America/New_York` entries for the same user are swept in one call. Invalidation is **per-user**; a write for user A cannot touch user B's cached entry (test-locked).
- **Day-rollover is a free miss.** `today_iso` is part of the cache key, so a request on a new local calendar day is a natural miss and rebuilds `weeks_until_race`, `current_week_number`, `today` from fresh values without any explicit invalidation.
- **Schema-version bumps are a free miss.** The key embeds `USER_CONTEXT_SCHEMA_VERSION`, so a deployed rev that bumps the payload shape cannot serve stale `v=1` payloads out of a long-running worker's cache — it's a natural miss and rebuilds against the new shape. Test-locked via `test_cache_module_schema_version_bump_is_a_cache_miss`.
- **Test coverage.** `tests/test_user_context_cache.py` — 19 tests across three layers:
  1. **Module primitives** — `set_cached` / `get_cached` / TTL expiry / TTL=0 / error-envelope rejection / `invalidate_user_context` / schema-version bump.
  2. **Tool-boundary dedup** — second call within the same `(user, tz, today)` window does NOT re-invoke `build_user_context_payload` (spied); different `tz` / different `today` are cache misses; errors are not cached (fixes a `no_user`→seed→re-read flow that would otherwise be stuck).
  3. **Write-path invalidation** — end-to-end through `tool_save_coach_preference` (the pre-test cache entry is gone after the write; other users' entries are untouched) + source-level lock that the invalidation call is still present in both write tools (prevents silent drift on future refactors).
- **Global cache-clear autouse.** Added an autouse teardown fixture in `tests/conftest.py` that wipes module-level caches (currently just `user_context_cache`) between every test so cross-test pollution is prevented. Added here (not just in the cache test file) because `test_get_user_context_tool.py` and `test_user_context_contract.py` both exercise the tool multiple times per session; without it, their assertions on different fixture data would see stale cache hits.

### 3B.13 — Orchestrator opening-turn nudge (2026-04-21)

- **Prompt-section helper.** `src/smartcoach_mobile_coach/orchestrator.py::_user_context_opening_nudge_section(directive, plan_creation_mode)` — emits a compact Markdown section when `directive.turn_type == TURN_OPENING` and we are NOT in `plan_creation_mode`. Returns empty string otherwise. Wired into the primary system-content composition immediately after `_intent_priority_override_section` so intent-level overrides stay above it in the prompt stack.
- **Why opening only.** The nudge tells the coach to call `get_user_context` *once* at the start of a conversation so PLAN→ACTUAL→GAP→ACTION reasoning (§19.2) has the race goal / current phase / `phase_kpi_priority` / `baseline_status` / `coaching_level` grounded from turn one. Repeating the call on `follow_up` or `drill_down` is wasteful (same payload is in the per-request `tool_result_cache`), so the section explicitly tells the coach **not** to re-call on same-thread follow-ups.
- **Why suppressed in plan-creation mode.** Plan intake has its own dedicated prompt stub (`_plan_creation_directive_stub`) driving a narrow collect-race-date → collect-days → confirm flow. Pulling a full context payload there adds noise without helping the intake flow, and risks the coach pivoting to "let me tell you about your training" when it should be asking the next intake question.
- **Soft hint, not a hard rule.** The section explicitly carves out narrow fact-lookup openings ("what was my last run's HR drift?", "when was my last marathon?") — those go straight to `get_run_summary` / `find_runs_by_date` / `search_runs` without a detour through `get_user_context`. Test-locked via `test_nudge_carves_out_fact_lookup_openings`.
- **Test coverage.** `tests/test_orchestrator_user_context_nudge.py` — 7 tests: emit on `TURN_OPENING`; suppress on every other turn type; suppress in `plan_creation_mode=True`; mentions the small payload + caching so the model actually takes the hint; fact-lookup carve-out wording is present; no-re-call-on-follow-up wording is present; section coexists cleanly with `_intent_priority_override_section` in the composed prompt.
- **No behavior change for non-opening turns.** Follow-up, drill-down, acknowledgment, clarification, and new-topic turns are byte-identical to pre-3B.13 system prompts. Plan-creation turns (every `turn_type` variant) are likewise unchanged.

### 3B.7 — Display-ready strings across plan tools (2026-04-21)

- **Goal.** Per Topic 4, the coach should never have to render numeric fields — paces, heart rates, distances, percentages — into user-facing strings on its own. Every plan-aware tool now emits a parallel `display.*` sub-dict alongside the raw numeric fields so the LLM can quote spec-correct, locale-correct strings (`8:45/mi`, `142 bpm`, `5.00 mi`, `72 %`) with zero formatting work.
- **Additive, never destructive.** Display dicts are **siblings** of the `planned` / `actual` (or equivalent) blocks — the original numeric payloads are byte-exact copies of the source data. Single-source-of-truth (§X.5) is preserved: `run_insight.execution_block_to_*_shape` and the three plan-service builders remain the sole producers of the numeric data; the display layer only reads them and renders.
- **Scope.** `execution_block_to_weekly_plan_shape` + `execution_block_to_insight_summary_shape` (per-run display); `build_weekly_plan_payload._build_future_week_day_entry` + `_build_past_current_day_entry` (per-day planned.miles + target_hr passthrough); `build_plan_overview_payload` (total_planned_miles, per-phase total_miles, per-week volume_curve.planned_miles_total, per-week long_run_miles); `build_phase_analysis_payload` (per-run-type miles_planned_total, miles_actual_total, zone_compliance_pct_avg, completion_miles_pct_avg + phase_weeks.completion_pct).
- **Helper extensions.** `src/smartcoach_mobile_coach/display_format.py` gained `format_hr_range_bpm` (e.g. `138–150 bpm` with en-dash) and `format_percent` (`decimals` kwarg; accepts either fractional or already-percent scales). Both handle `None` ⇒ `None` gracefully so error/missing rows don't inject em-dashes into user numbers.
- **Testing.** `tests/test_plan_tool_display_strings.py` — 24 contract tests pinning helper output for distance / HR / pace / percentage, and verifying `display` presence + exact formatting across every surface above. Parity test updated: `test_insight_summary_shape_parity_with_pre_0a_dict_literal` now asserts the new `display` block is present with all seven formatted fields — proves the shape is frozen.
- **No backend-side numeric drift.** Every `display.*` value is a pure read from an already-produced numeric field in the same payload. This means a future tweak to a numeric producer automatically flows to the display layer (no dual-update path), and display-string regressions become test failures in both layers simultaneously.

### 3B.8 — Plan-tool cache with plan-regen invalidation (2026-04-21)

- **Goal.** Per Topic 5, plan-aware tools must be cache-friendly for past/current-week repeat reads and must invalidate on adaptation rewrites. Three tools (`get_weekly_plan`, `get_plan_overview`, `get_phase_analysis`) are now backed by a shared per-user cache with explicit plan-regen invalidation.
- **Dedicated module.** `src/smartcoach_mobile_coach/plan_cache.py` — module-global dict guarded by `threading.Lock`, TTL via `SMARTCOACH_MOBILE_PLAN_CACHE_TTL` (default 300 s). `PLAN_CACHE_SCHEMA_VERSION = 1` is embedded in every key so a deploy that reshapes any plan-tool payload is a natural miss (the spec change is visible in git). Mirrors the `user_context_cache` / `insight_cache` pattern the repo already uses.
- **Key design.** `(user_id, kind, tz, today_iso, extra, schema_version)` where `kind` is the tool name (so `weekly_plan` / `plan_overview` / `phase_analysis` entries never collide) and `extra` carries tool-specific axes — `week_start_iso` for weekly_plan, phase key for phase_analysis, empty for plan_overview. `user_id` is the prefix so `invalidate_user_plan_cache(user_id)` can sweep every kind + every axis for one user in one pass without touching other users' entries.
- **Day-rollover is a natural miss.** `today_iso` embedded in the key means a request on a new local calendar day rebuilds `week_temporality`, phase-to-date cutoffs, and per-week completion counts correctly with zero extra code. Past-week payloads are byte-identical day over day, so the first-of-day rebuild is cheap and every other request in the day is a hit.
- **Invalidation on plan regen.** `tool_generate_training_plan` now calls `plan_cache.invalidate_user_plan_cache(user_id)` immediately after the new plan commits — paired with the existing `user_context_cache.invalidate_user_context` call at the same post-commit point. The net effect: a brand-new plan (new phases, new long-run day, new workout set) is visible in the very next read from every plan tool, no TTL wait.
- **Activity-landing staleness is TTL-bounded.** Current-week payloads DO change when a matched activity lands; rather than plumb an invalidation hook into every activity-upload path (which the repo's `metrics_cache_service` also leaves to TTL), the 5-minute TTL caps staleness. Acceptable for V1.6 — activities typically land between chat turns, not during one.
- **Tool-boundary wiring.** Each of the three tools resolves `today_iso` through its service module's `get_today_date_in_timezone` binding (so existing autouse test fixtures that pin today at the service layer automatically pin the cache key), checks for a hit, and on miss falls through to the existing service builder and caches the result. Error envelopes (`{"error": "no_plan", ...}`) are explicitly NOT cached to avoid serving a stale transient after the underlying data was just seeded.
- **Test coverage.** `tests/test_plan_cache.py` — 23 contract tests: set/get round-trip, miss semantics, error envelopes never cached, TTL-zero disables, TTL expiry evicts, `invalidate_user_plan_cache` drops every kind + extra for one user and leaves other users alone, schema-version bump is a miss, key isolation across kinds / weeks / phases / timezones / users, `tool_get_weekly_plan` / `tool_get_plan_overview` / `tool_get_phase_analysis` second call in the same window is a cache hit (service builder call count = 1), phase-id is case-insensitive (`"Base"` and `"base"` hit the same entry), `invalid_user_id` / `missing_phase_id` short-circuit BEFORE the cache layer (no orphan entries), day-rollover forces a rebuild, different week keys are separate cache entries, plan-regen simulation: invalidation drops the old entry and the next call produces a fresh payload. Global `_clear_module_level_caches` autouse fixture in `tests/conftest.py` was extended to also call `plan_cache.clear_all()` so prior-test cached entries never leak into unrelated tests.
- **No behavior change when cache is cold.** Byte-exact payload parity with the pre-3B.8 path for every error envelope AND success payload; the cache only deduplicates identical reads.

### 0.C — `get_weekly_training_insight` no-new-consumers enforcement (normative)

Status: **Deprecated 2026-04-21.** Replacement is `get_weekly_plan` (Phase B, V1.7).

**Policy:** No PR may introduce a new caller of `tool_get_weekly_training_insight`, a new entry referencing the handler key `"get_weekly_training_insight"` outside the single existing dispatch line, or any new system-prompt snippet that instructs the LLM to prefer this tool. Existing consumers are preserved during V1.6 so live coach flows do not break.

**Enforcement mechanisms** (in order of precedence):

1. **Runtime — DeprecationWarning.** `tool_get_weekly_training_insight()` emits `DeprecationWarning` via `warnings.warn(_GWTI_DEPRECATION_MESSAGE, DeprecationWarning, stacklevel=2)` on every call. The message cites `V1.6`, `0.C`, and names `get_weekly_plan`, making it grep-able in CI logs and log aggregators.
2. **Test lock-in.** `tests/test_get_weekly_training_insight_deprecation.py` pins:
   - exactly one `DeprecationWarning` per invocation,
   - the message mentions the replacement tool and cites `0.C`,
   - the return contract is behavior-preserved,
   - callers may filter the warning when they intentionally consume it.
   Dropping the warning or weakening the message turns the suite red — forcing a deprecation-policy conversation.
3. **Code-review checklist.** Reviewers flag any PR that (a) imports `tool_get_weekly_training_insight` outside `agent_tools.py`, (b) adds a new entry with the handler-key string, or (c) adds a new `orchestrator.py` system-prompt rule that tells the LLM to reach for this tool.
4. **LLM-facing signal.** The OpenAI tool description in `scripts/setup_coach_tools.py` now opens with `[DEPRECATED — will be replaced by get_weekly_plan …]`. The tool remains enabled and callable so live conversations keep working.

**Known current consumers** (grandfathered, do not expand):
- `src/smartcoach_mobile_coach/agent_tools.py` — the tool function, the `_TOOL_HANDLERS` dispatch entry, and the `execute_tool` handler-key branch.
- `src/smartcoach_mobile_coach/orchestrator.py` — system-prompt snippets (lines ~631, 657, 660–663, 856, 863, 1307). Rewrites happen in Phase C–F once `get_weekly_plan` is available.
- `scripts/setup_coach_tools.py` — OpenAI tool schema registration.
- `tests/test_weekly_insight_lazy_payload.py` — existing behavior tests (kept, now also surface the deprecation warning in pytest summary).

Any consumer not in this list is a new consumer and must be rejected in review.

> **Enforcement:** Each producer module has 100 % test coverage for the rules in the spec it implements. No other file in the repo re-computes these values. Grep check during code review: a commit that introduces `pct_above` arithmetic outside `deviation.py` fails review.

Actual paths above are **proposed locations**. If existing architecture already has a better home (e.g. an existing `scoring/` package), colocate. The rule is **one producer per field**, not the specific path.
